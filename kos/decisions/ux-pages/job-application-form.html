Public Job Application Form — three recommendations

The actual public, unauthenticated page from projects/hris/features/recruitment-ats/PLAN.md's core flow step 2 — "candidate applies via that form." No account, no login, no internal HRIS chrome — the SME's own job posting on JobStreet/ Indeed/LinkedIn points its Apply button here, and this form's only job is capturing the candidate into the database. Fields match the plan's fixed list exactly: name, email, phone, résumé upload, optional note.

Illustrative branding, not a design-system decision: shown as "Alon Pay," a placeholder PH fintech employer using HRIS — in production this page is white-labeled to whichever SME posted the job, not to HRIS's own brand. Kept on decisions/ui/color-palette-ink-and-amber.md's tokens here purely so the three options compare on identical colors, not because that's the intended real customer-facing palette. Also added, not in the plan's fixed field list: a Data Privacy Act (RA 10173) consent checkbox — standard practice for PH forms collecting personal data, flagged here for confirmation rather than assumed decided. Résumé upload is a static dropzone mock, not a working file picker. Validation follows decisions/ui/form-validation-inline-only.md — a demo toggle on Options 1–2 previews one inline error; a "preview after submitting" toggle shows the confirmation state per decisions/ui/empty-states-guided.md (icon, headline, one line, no CTA — there's nothing else for the candidate to do next).

Why this one

The full job description sits right above the form, in one reading order — no split attention, nothing to scroll back to. Fastest to build and the most familiar pattern for a one-time, unauthenticated form a candidate fills out once and never returns to.

Trade-off

On a long job description the form gets pushed well below the fold, especially on mobile — a candidate skimming the ad may not immediately see there's a form to fill in at all.

Why this one

Splits a form with a file upload and a consent checkbox into three short screens instead of one long one — each step feels quick to finish, and Step 3's review catches typos before anything is submitted. The confirmation is naturally the wizard's own last step, not a separate state to bolt on.

Trade-off

Three screens and two extra clicks (Continue ×2) for what's fundamentally a five-field form — more building and more places for a candidate to abandon partway through than Options 1–2's single scroll. No inline-validation demo modeled here since a real version would need step-level validation before "Continue" advances, which is more logic than this static comparison shows.
