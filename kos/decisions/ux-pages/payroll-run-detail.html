Payroll Run Detail — three recommendations

Where an HR Admin lands after clicking into a run from payroll-runs.html — line items per employee for one cutoff, plus the run/finalize action from the payroll v2 plan's step 6 ("computes net pay, generates a payslip"). What changes across the three is how editing one employee's line items — the actual task on this screen — happens without losing the roster view of everyone else in the run.

Grounded in the same run shown open in payroll-runs.html: Aug 16–31, 2026 cutoff, pay date Sep 5, 2026, status Open, 42 active employees, gross so far ₱948,000.00 (provisional — this page is exactly where that figure comes from, computed live off line items entered so far). Table below shows 10 of the 42 for space; figures are illustrative placeholders. Mikaela Santos's row reuses the exact numbers from my-payslips.html (base ₱22,500.00, Pag-IBIG MPL loan amortization ₱1,200.00, net ₱18,200.00) so the two mockups agree. 3 employees — Carlo Bautista, Ferdinand Ocampo, Jonas Rivera — are missing OT entries, matching payroll-runs.html's hero flag; their net pay can't compute until resolved. Loan lines auto-add from each employee's loan ledger and count down (decisions/cash-advance-vs-loan-ledger-distinction.md); statutory deductions (SSS/PhilHealth/Pag-IBIG/BIR) are looked up from editable rate tables, a separate not-yet-built page (decisions/statutory-deductions-as-editable-data-not-code.md) — shown here read-only. There is no approval step before finalizing — the HR Admin who ran payroll finalizes it directly (decisions/approval-chains-scrapped-fallback-design.md); finalizing uses pessimistic locking + idempotency so a double-click can't double-process (decisions/rails-db-transactions-locking-idempotency.md). Status badges follow decisions/ui/badge-system-four-categories.md: "Missing OT" → Caution, everything else deviation-free shows no badge. Viewing persona: Andrea Cruz, HR Admin.

Why this one

Everyone stays in one flat scan order — nothing hidden behind a click before you even know it needs attention. Reuses payroll-runs.html Option 3's expandable-row mechanic and my-payslips.html's breakdown-list styling verbatim, so the "tap a row, see the full breakdown" gesture is already familiar from two other screens by the time an admin reaches this one.

Trade-off

Editing several employees in a row means repeatedly scrolling past everyone else's numbers to reach the next flagged row — fine for the occasional adjustment, tedious for a payroll cutoff where five or six employees genuinely need line items touched.

Why this one

Reuses time-attendance.html's chosen drawer mechanic exactly (decisions/ui/time-attendance-attendance-first-templates-drawer.md) — the master table stays the scannable source of truth (base salary, net pay, status at a glance for all 42), and editing one employee's line items opens beside it rather than replacing it, so an admin never loses their place in the list. Drawer shown open here on Mikaela Santos purely for this comparison; a real visit starts closed.

Best when

Payroll editing is naturally a "fix a handful, glance at the rest" task — most cutoffs, most employees need zero changes. The drawer keeps that majority path (scan, confirm, move on) cheap, and pays a small tax (open/close) only on the employees that actually need a line item touched — the same trade-off already made for shift templates.

Why this one

Reuses team-reviews.html's split-editable-detail pattern verbatim (decisions/ui/team-reviews-split-editable-detail.md) — the roster stays permanently visible on the left with net pay or a Missing OT badge per name, so an admin working through several flagged employees in sequence just clicks down the list instead of repeatedly opening and closing a drawer or scrolling past finished rows.

Trade-off

Fixed two-column layout eats more width than a plain table or a drawer that stays closed by default, and a 42-row roster list needs its own scroll — workable at comfortable density, but this is the option that leans hardest on vertical space for a screen an admin may revisit several times per cutoff.
