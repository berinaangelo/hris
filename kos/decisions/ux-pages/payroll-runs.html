Payroll Runs — three recommendations

The HR-Admin landing page for Payroll (Company → Payroll, decisions/ui/navigation-me-team-company.md), first screen of payroll v2 per projects/hris/features/payroll-v2/PLAN.md. A run history list, one row per semi-monthly cutoff, that also carries the plan's step 1 — "HR opens a pay period." What changes across the three is how much weight the in-progress run gets versus the finalized history sitting below it. Clicking into any run — to add line items, review, or finalize — goes to Payroll Run Detail, a separate not-yet-built page; nothing here edits a run directly.

Ahead of the roadmap, on purpose: payroll v2 engineering is still deferred until after v1 ships, but per kos/decisions/ui/navigation-me-team-company.md the Payroll nav slot is already reserved and my-payslips.html / my-payslips.html's employee-side figures were built ahead of schedule the same way — this is that same nav slot's HR-Admin counterpart, and the first page in the user's own build order for Payroll (v2). Viewing persona: Andrea Cruz, HR Admin. 42 active employees, semi-monthly cutoffs (PH standard), today is Aug 22, 2026 — the Aug 1–15 cutoff shown finalized here reuses the exact figures from my-payslips.html (Mikaela Santos, net ₱18,200.00), so the two mockups agree with each other. Only one run can be open at a time — a real business rule, not a UI choice — and finalizing uses pessimistic locking + idempotency per decisions/rails-db-transactions-locking-idempotency.md so a double-click can't double-process. Status badges follow decisions/ui/badge-system-four-categories.md exactly: Open → Neutral, Finalized → Positive. The Dec 24 row is the 13th Month Pay run (decisions/thirteenth-month-pay-mandatory-in-ph.md) — same cadence as every other row, just flagged by type. Rate tables (SSS/PhilHealth/Pag-IBIG/BIR) are a separate future page, not shown here — decisions/statutory-deductions-as-editable- data-not-code.md. All figures are illustrative placeholders.

Why this one

The most literal read of the plan's own wording — "payroll run history (read-only after finalized)." Same table/toolbar/badge components already decided elsewhere (compliance-certifications.html, company-reviews.html). "Open new pay period" sits where every other list's primary action sits, disabled with an explanatory note when a run is already open rather than hidden — so the one-open-run-at-a-time rule is visible, not a silent restriction.

Trade-off

The open run is just the first row with a highlighted rail — nothing distinguishes "this needs your attention right now" from "here's what already happened" until a skimming admin reads the Status column, the same trade-off compliance-certifications.html's Option 1 accepted for expired certs.

Why this one

The plan's own step 1 — "HR opens a pay period" — is the entire reason this screen exists, so the open run gets the same top-of-page treatment my-payslips.html gave the latest payslip and compliance-certifications.html gave expired/expiring certs: the one thing that actually needs a click, fully surfaced, before any history. Best when

There's realistically at most one open run at a time — this screen's main job on most visits is "get back into the run I'm building," not browsing history. Costs a fixed slice of vertical space to the hero even on the rare visit with nothing open (that state just needs its own empty-ish "no run open — start one" version of the card, not shown here).
