Variable/method/class names across the HRIS codebase should make what
they do / what they're for / why they exist understandable at first
glance — no digging into the implementation, no comment required to
explain the name. This applies the project's own "grandma test" (from
[[../projects/hris/PLAN.md|the v1 plan's five-gates check]] — originally
about the product flow needing no explanation) to naming as well.

**How to apply:**
- Prefer a slightly longer, plain-English name over a short, clever, or
  abbreviated one (`assign_manager` not `asgn_mgr`; `overdue_reviews`
  not `stale`).
- Name for intent/purpose, not implementation detail
  (`send_decision_email` not `deliver_now`).
- If a name needs a comment to be clear, rename it instead of adding
  the comment.
- Applies alongside
  [[rails-metaprogramming-for-repetitive-methods]] — metaprogrammed
  methods still need to resolve to a self-evident name at the call
  site (`approved?`/`approve!` read clearly even though generated by a
  macro).
